# Aeza Risk — анализатор рисков оттока

Панель для маркетолога. Отвечает на три вопроса: **кому из клиентов нужно внимание**, **почему возникает риск** и **сколько денег
бизнес может потерять**. Расчёт идёт по аккаунтам, услугам и транзакциям и обновляется сам при изменении данных, весов модели и
с течением времени. Открытые вкладки панели обновляются без перезагрузки. Основной балл по умолчанию считает ML-модель
(вероятность непродления × 100); правила с настраиваемыми весами включаются на странице «Модель».

Данные приходят только событиями, как от настоящей системы-источника. Их присылает симулятор: сначала передаёт начальный snapshot системы
(тестовые данные организаторов или сгенерированных клиентов с историей), затем ведёт его вживую без пауз. Настройки симуляции,
пересоздание snapshot системы и конструктор событий — на странице «Симуляция».

Продакшен: <https://inmovery.dev> (вход по логину и паролю), Swagger — <https://inmovery.dev/api/v1/docs>.

## Запуск

Нужен Docker с Compose v2.

1. Создайте `.env` из примера:

   ```bash
   cp .env.example .env
   ```

   Задайте `POSTGRES_PASSWORD`, `APP_DB_PASSWORD`, `BOOTSTRAP_ADMIN_PASSWORD` (не короче 12 символов) и `INGEST_TOKEN` (им
   симулятор отправляет события). Пользователь только для чтения — `BOOTSTRAP_ANALYST_LOGIN` и `BOOTSTRAP_ANALYST_PASSWORD`.

2. Запустите:

   ```bash
   docker compose up --build -d
   ```

   Сначала стартует база, затем миграции, затем сервис и симулятор. Сервис начинает с пустой базы, симулятор передаёт событиями
   тестовые данные организаторов (`test_data_yandex/data.json`) и 50 дополнительных клиентов, после чего snapshot системы живёт: клиенты
   пополняют баланс, продлевают и бросают услуги. Перезапуск без `-v` данные, настройки и snapshot системы не теряет.

   `EVENTS_ONLY=false` в `.env` — прежний режим: тестовые данные загружаются снимком в пустую базу, симулятор ждёт.

3. Откройте <http://localhost:8080> и войдите логином и паролем администратора из `.env`.

### Стенд для разработки

```bash
docker compose -f docker-compose.local.yaml up --build -d
```

| Сервис | Адрес |
| --- | --- |
| Панель | http://localhost:8080 |
| API и Swagger | http://localhost:8081/api/v1/docs |
| Prometheus | http://localhost:9090 |
| Grafana | http://localhost:3000 |

Не запускайте одновременно с `docker-compose.yml`: совпадают порты.

Симулятор (`source-sim`) запускается вместе со стендом. Он сам опрашивает сервис (`GET /api/v1/simulation/agent`), берёт оттуда
настройки и шлёт события с токеном `INGEST_TOKEN`; сервис к симулятору не обращается. События симулятора помечаются как пришедшие из симулятора.

### Симуляция

Симуляция работает постоянно: паузы нет, после перерыва связи симулятор догоняет время. Страница «Симуляция» показывает, на связи ли
симулятор, фазу (передача начального snapshot системы, история, живой режим), часы snapshot системы, число клиентов и услуг,
отправленные события и очередь.

| Настройка | Когда применяется |
| --- | --- |
| Такт событий, шаг сценария, сбои доставки (повторы и перестановки) | Сразу, при следующем опросе симулятора |
| Snapshot системы: тестовые данные организаторов + N клиентов или сгенерированный snapshot системы (клиенты, дни истории), seed | После «Пересоздать snapshot системы» |

«Пересоздать snapshot системы» удаляет данные источника, журнал событий и результаты расчёта; пользователи, ревизии модели, ML-модели и аудит
остаются. Симулятор строит новый snapshot системы и передаёт его событиями. Пакеты старого snapshot системы, которые не успели дойти, сервис отклоняет
(`409 simulation_world_changed`). Кнопка «Запустить сценарий» проводит одного клиента через путь к оттоку по шагам.
Менять настройки может только администратор.

**Собрать событие.** Администратор выбирает тип (вход, пополнение, автопродление, выключение и включение сервера, смена тарифа,
удаление услуги, обращение, NPS, выгрузка бэкапа, изменение DNS, предложение удержания), клиента, услугу и поля события и нажимает
«Отправить в поток». Событие встаёт в очередь симулятора (`POST /api/v1/simulation/events`). Симулятор применяет его к snapshot
системы как действие самого клиента и отправляет в общий поток со следующим номером события аккаунта, затем сообщает итог: «в потоке»
с `eventId` или «не применено» с причиной (например, клиент уже ушёл). Дальше событие проходит обычный приём и пересчёт.

## Что в панели

- **Обзор** — выручка под риском, плановые продления и непокрытая часть на 30 дней; клиенты по уровням риска; три типа оттока:
  непродление, уход целиком, снижение платежей; прогноз продлений по неделям и факт из журнала событий.
- **Клиенты** — рейтинг с ID, email, балансом, суммой пополнений, score, уровнем, главной причиной и суммой под риском. Сортировка
  в обе стороны по ID, email, балансу, пополнениям, score и сумме под риском; фильтры, поиск, выгрузка в CSV.
- **Карточка клиента** — причины риска с вкладом каждого признака, расчёт денег по шагам, услуги и транзакции, история событий.
- **Модель** (администратор) — чем считается основной балл: **ML-модель** (по умолчанию) или **правила**. Пороги уровней, горизонт,
  время оценки и определения оттока настраиваются в обоих режимах. Веса признаков, окно срочности и предпросмотр без сохранения
  появляются после включения правил. Каждое изменение — новая ревизия: пересчитывает результат и сохраняется после перезапуска.
  Там же карточка ML-модели: проверка против правил, загрузка и замена пакета.
- **Источник** — состояние потока, журнал событий, импорт истории событий, загрузка тестовых данных снимком.
- **Симуляция** — состояние симулятора, его настройки, конструктор событий и пересоздание snapshot системы.

## API

Все маршруты, кроме `/metrics` и Swagger, требуют входа. Изменяющие запросы требуют заголовок `X-CSRF-TOKEN`
(выдаётся `GET /api/v1/auth/csrf`).

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/v1/auth/login` | Вход по логину и паролю |
| GET | `/api/v1/auth/me` | Текущий пользователь |
| POST | `/api/v1/auth/logout` | Выход |
| GET | `/api/v1/customers` | Рейтинг: `sortBy`, `sortDirection`, `riskLevel`, `search`, `page`, `pageSize` |
| GET | `/api/v1/customers/{id}` | Карточка клиента: услуги, признаки, причины, деньги |
| GET | `/api/v1/analytics/summary` | Сводка: уровни риска, деньги, прогноз |
| GET | `/api/v1/model/settings` | Действующие настройки модели |
| PATCH | `/api/v1/model/settings` | Изменение настроек → `202` и пересчёт |
| PUT | `/api/v1/source/snapshot` | Загрузка тестовых данных (полная замена) → `202` и пересчёт |
| GET | `/metrics` | Метрики Prometheus: клиенты по уровням, деньги, номер расчёта |
| GET | `/api/v1/docs` | Swagger UI |

Дополнительно: приём событий `POST /api/v1/source/events`, импорт истории `POST /api/v1/source/events/import`, выгрузка
`GET /api/v1/export/customers`, предпросмотр модели `POST /api/v1/model/preview`, статус ML-модели `GET /api/v1/ml/status`,
переключатель основного балла `PUT /api/v1/ml/scoring` (`rules` | `ml`),
симуляция `GET /api/v1/simulation`, `PUT /api/v1/simulation/settings`, `POST /api/v1/simulation/reset`,
`POST /api/v1/simulation/scenario`, конструктор событий `GET /api/v1/simulation/events/types`, `POST /api/v1/simulation/events`,
`GET /api/v1/simulation/events` и маршруты симулятора `/api/v1/simulation/agent` (только с `INGEST_TOKEN`).
Полный список — в Swagger и [contracts/openapi.json](contracts/openapi.json).

Пример загрузки тестовых данных:

```bash
curl -X PUT "http://localhost:8080/api/v1/source/snapshot?sourceAsOf=2026-10-19T15:00:00Z" \
  -H "Authorization: Bearer $INGEST_TOKEN" -H "Content-Type: application/json" \
  --data-binary @test_data_yandex/data.json
```

## Как добавить признак

1. Создайте класс в `src/Aeza.Risk.Core/Features/`:

   ```csharp
   public sealed class LowReplenishmentFeature : IRiskFeature
   {
       public string Key => "low_replenishment";
       public string Title => "Мало пополнений относительно цены";
       public string Description => "1, если всего пополнено меньше трёх оплат услуги";
       public decimal DefaultWeight => 10m;

       public FeatureValue Evaluate(ServiceContext ctx)
       {
           if (ctx.Account.TotalReplenished is not { } total || ctx.Service.Price is not { } price)
               return FeatureValue.Missing("Нет totalReplenished или цены", "account.totalReplenished", "price");
           return total < 3 * price
               ? FeatureValue.Of(1m, $"{ctx.Service.Name}: пополнено {Fmt.Eur(total)} — меньше трёх оплат по {Fmt.Eur(price)}")
               : FeatureValue.Of(0m, $"{ctx.Service.Name}: пополнений достаточно");
       }
   }
   ```

2. Добавьте `new LowReplenishmentFeature()` в `FeatureCatalog.All`.
3. Добавьте тест в `test/Aeza.Risk.UnitTests`.

Редактор весов, причины, деньги и API подхватят признак сами. Пока администратор не задаст вес, у нового признака вес 0.

## Развёртывание

- `docker compose --profile tls up -d` — nginx с HTTPS (задайте `DOMAIN`), `--profile observability` — Prometheus и Grafana.
- Kubernetes (k3s): Helm-чарты в `deploy/helm`, значения для продакшена — `deploy/k8s/values/production`.
- CI — `.gitlab-ci.yml`: сборка образов, выкатка вручную, откат.
- Смена пароля: `docker compose run --rm -e NEW_PASSWORD='…' migrator set-password admin` (сессии пользователя отзываются).

## Ограничения

- В режиме правил score — индекс приоритета, а не вероятность ухода; веса по умолчанию экспертные и меняются в панели.
  В режиме ML score — вероятность непродления × 100; услуги вне окна модели получают «нет оценки», а не 0.
- В тестовых данных нет истории статусов и дат удаления, поэтому прошлый отток не рисуется. Факты появляются из потока событий
  после его подключения.
- Транзакции тестового набора созданы вместе с услугами, поэтому тренд платежей на нём почти везде «мало истории».
- Шесть услуг `prolong_wait` в наборе просрочены больше чем на 5 дней. Они помечены флагом качества данных, статус не переписывается.
- По умолчанию оценка идёт на текущее время, а тестовые данные датированы 19.10.2026. Режим «на момент выгрузки данных» включается
  в настройках модели.
- ML-модель обучена и проверена на журнале симулятора за 10 лет. Пакет `tools/Aeza.Risk.Ml/models/fasttree-1500x3650/model-bundle.zip`
  входит в образ и загружается при первом запуске; заменить его можно на странице «Модель». Без загруженной модели расчёт идёт
  правилами, а панель показывает почему. Результаты — в [описании расчёта](docs/scoring.md#ml-модель).
